# 1.2.0 编辑器分拆设计（Input 表单 / Editor 编辑器 / TextCore 共享核）

> 决策状态：已决定分拆（"杀鸡不用牛刀"），本方案为执行依据。
> 约束：开发阶段，直接改不做兼容；每阶段 `cargo test -p rgpui` 全绿 + 中文 IME 手测。

## 0. 结论先行

抽 **TextCore 共享核** + 组合（`InputState` / `EditorState` 各持有一份），**不复制**。
顺序：P0 feature 门（几天）→ P1 抽核（1~2 周）→ P2 渲染分层（1~2 周）→
P3 Editor 落地 + `code_editor` mode 退役（1 周）。`crate` 化暂不做，
先模块后 crate（外部复用出现时再提）。

> M1 追认（P3a 实际路线）：`EditorState` 未按 §4 原方案直连 `TextCore`，
> 而是包 `Entity<InputState>` 的编排外壳（大纲缓存/符号跳转/高亮透传）——
> `Context<EditorState>` 与 `Context<TextCore>` 不互通，Deref 方案的手工
> delegate 活比预期大；包装实体零对外 API  churn，差集走透传方法补。
> §4 原架构图保留作"已放弃方案"备查，§5 P3 按实际路线结算。

## 1. 动机量化

`InputState` 公开方法约 70 个：表单专属约 20（masked/pattern/validate/
number/step/min/max/loading/mask…），编辑器专属约 25（fold/行号/行注释/
auto_close/bracket_match/current_line/document_symbols/goto_symbol/
set_highlighter/reveal_*/multicursor/line_ops…），共享约 25。
表单用户为 20 个方法拖进 25 个编辑器方法——分拆不是洁癖，是 API 事故。

## 2. 现状盘点（分拆可行性证据）

1. **特性实现已是独立文件 + `pub(super)`**：line_ops/multicursor/auto_close/
   bracket_match/current_line/context_menu 全是模块内方法，对外只有
   state.rs 里十几个 builder——搬运边界现成，无需解纠缠。
2. **消费方只用基础 API**：combobox/sender/tag_input/otp/search_panel 等
   12 个消费方全是 `new + placeholder + 单行行为`，分拆后原地不动。
3. **渲染是 mode 分支不是交织**：`element.rs` 约 20 处
   `is_single_line/is_code_editor` 开关，拆渲染就是把分支掰成两个函数。
4. **trait 扩展模式已跑通**：`Highlighter::document_symbols` 默认空实现，
   tree-sitter 后端覆盖；`TextDecorationCollection` 被 bracket/current_line/
   search 三家复用；`actions!` + keymap 加新动作不动分发。

## 3. 可扩展性设计（编辑器功能只会越来越多）

未来功能（minimap/vim/snippets/inlay hints/sticky scroll）必须满足：
**加新能力只加新文件，不改核心文件**（开闭原则）。已验证可用的机制继续用，
缺的三件本次补齐：

### 3.1 已有机制（沿用，写进规范）

- 能力 trait：`Highlighter`（语法/折叠/大纲数据源），新后端实现 trait 即可；
- 装饰集合：任何行内标记走 `TextDecorationCollection`，不碰渲染；
- 动作键位：`actions!` + keymap 上下文，新动作自带默认键与文档；
- 投影复用：`DisplayMap` 折叠投影给所有需要行映射的功能共用。

### 3.2 缺失机制（本次补齐，否则每个新功能都是一次 IME 式事故）

> M1 结算：5 件中 2 件落地（funnel P1b / overlay P2），3 件砍掉——
> `on_edit` 订阅表与 `extensions` 表：当前编辑器功能数（行操作/多光标/闭合/匹配/
> 当前行/右键菜单）经现有 `Change` 订阅 + 结构体小字段已够用，为"未来功能"预建
> 总线属于过度设计，砍；keymap `vim` 命名空间预留：vim 本身 1.2 非目标，预留无意义，砍。
> 本节原文保留备查（机制思想 M2–M6 加新功能时按需重提）。

1. **编辑 funnel 单一化**：现状两入口（`replace_text_in_range` /
   `replace_and_mark_text_in_range`）。高亮刷新曾只接前者、漏掉后者，
   直接导致中文输入崩溃（见 1.2 修复记录）。规范：文本变更只走一个 funnel
   出口，新功能不许各自接线。
2. **`on_edit` 订阅表**：funnel 出口统一触发 `Vec<EditHook>`（只读快照），
   bracket/current_line/highlight/multicursor 的刷新逻辑从"改 funnel 代码"
   改为"订阅 hook"。新增功能默认走订阅，duplicate 刷新用合并标记去重。
3. **类型化扩展存储**：`extensions: HashMap<TypeId, Box<dyn Any>>` +
   `ext::<T: Default>()`（抄 `App::globals_by_type` 现成模式）。
   新功能状态一律进扩展表，`InputState` / `EditorState` 结构体不再膨胀。
4. **渲染覆盖层列表**：gutter/折叠图标/空白符/minimap（未来）注册为
   overlay 渲染函数，共享同一份布局数据，不再各自改 `prepaint`/`paint`。
5. **keymap 上下文约定**：特性动作统一 `"Input"` 上下文（现状），vim 等
   模态需求预留 `"input:vim:<mode>"` 命名空间；新增默认键必须附 keymap
   冲突单测（`keymap.rs` 现有测试即模板）。

### 3.3 可维护性红线（写进 AGENTS 备查）

- `state.rs` 单文件超 3000 行即触发再拆分（本次 P1 后应回落到 2000 内）；
- 新编辑器功能必须自带：独立文件 + `pub(super)` 实现 + builder 开关 +
  中文文档注释 + 与 multicursor/undo/IME 交互的单测；
- 特性组合矩阵：multicursor ×（auto_close/电缩进/粘贴）已明确不扇出，
  后续每对交互必须文档注明（是特性还是 bug，只差这一行字）。

## 4. 目标架构

> M1 结算：本节原方案（`EditorState{core}+Deref`）已放弃，实际落地见 §4.1。
> 原文保留备查。

```text
input_ui/
  core.rs        ← 新抽：TextCore（Rope + 选区/光标 + History + 基础编辑/撤销
                   + IME + 剪贴板 + on_edit hooks + extensions 表）
  state.rs       ← 瘦身后 InputState { core + 表单字段 }（校验/掩码/number/password）
  editor.rs      ← 新建：EditorState { core + gutter/折叠/多光标/大纲… }（字段能进
                   extensions 表的不进结构体）
  input.rs       ← Input 组件（表单渲染，不变）
  editor_ui.rs   ← 新建：Editor 组件（gutter/折叠/行号 + overlay 列表）
  line_ops.rs / multicursor.rs / auto_close.rs / … ← 实现平移到 EditorState，
                   方法签名不变（self 类型换一下）
```

组合不复制：`EditorState` 持有 `TextCore`，`Deref<Target = TextCore>` 保证
`text()` / `replace()` 等调用姿势不变；`entity.update` 边界处用显式 delegate
（`Context<EditorState>` 与 `Context<TextCore>` 不互通，这是唯一的手工活）。

### 4.1 实际落地路线（P3a，M1 追认即最终路线）

```text
input_ui/
  core.rs            ← TextCore（文本/选区/历史/装饰/IME，InputState 组合持有，P1a/P1b）
  input/             ← 表单侧：state.rs（InputState）+ element.rs + 动作/键位定义
  editor/            ← 编辑器侧（editor feature 门控）：state.rs（EditorState）+
                       editor_ui.rs（Editor 组件 + overlay：折叠图标/多光标）+
                       line_ops.rs / multicursor.rs / auto_close.rs /
                       bracket_match.rs / current_line.rs（全部仍 `impl InputState`，
                       方法签名不变，self 类型没换——换类型省的行数抵不上调用点 churn）
  input_ui/ 根       ← 共享小模块（change/cursor/history/decorations/IME 等，不动）
```

`EditorState { input: Entity<InputState>, outline: Vec<DocumentSymbol> }`（编排外壳）：
创建时一次配好代码编辑配置（多行 + 行号 + 折叠 + 引导线 + 键入体验四件）；
唯一真相源仍是内部 `Entity<InputState>`（文本逻辑零复制，IME 三连 panic 教训守住）；
旧 `CodeEditor` 用户能力差集走透传方法补（`set_value`/`reveal_*`/`set_read_only`/
`set_line_comment_prefix`/`set_highlighter`/`goto_symbol`，M1 清单；`set_highlighter`/
`set_value` 补刷大纲——内部实现压住 `Change` 事件，外壳补偿）；
`Editor` 组件 = `Input` 组件复用 + 状态行（行操作/多光标/右键菜单经 `Input` 元素接线全可用，无需透传）。
放弃 Deref 的理由：`Context<EditorState>` 与 `Context<InputState>` 不互通，
每个跨实体方法都要手写 delegate，还要处理双重订阅/通知——包装实体把这笔钱省了，
代价是多一层 `input()` 下沉口（留给确实需要 `Entity<InputState>` 的 API，如
`SearchPanelState::attach_editor`）。

## 6. 风险与对策

| 风险 | 对策 |
|------|------|
| 选区/光标与编辑 ops 交织最深，切分线画错全崩 | P1 先定 `TextCore` 字段清单并评审；`backspace/replace` 首批搬运+单测锁定 |
| 渲染分层破坏软换行/折叠投影 | P2 只搬不改逻辑，逐个 overlay 开关对比（特性开关全关 = 原样） |

## 7. 决策记录

- 不复制：8000 行共享核复制两份，等于买双倍 bug（IME 三连 panic 教训）。
- 先模块后 crate：`crate` 化等 rgpui 之外的复用出现再提，现在拆包只有成本。
- `CodeEditor` mode 退役不兼容：开发阶段，直接删（既定规则）。
- `TextArea` 缺失（AGENTS 索引有、代码无）：P3 时按多行表单补，归 Input 侧。
- M1 追认包装实体（§4.1）：Deref 跨 `Context` 的 delegate 手工活比省下的行数贵，
  且 `Input` 元素复用（`Editor` 包 `Input`）已让行操作/多光标/右键菜单零透传可用——
  分叉点只剩"状态透传差集"，包装实体是局部最优。
- M1 砍 `on_edit` 订阅表 / `extensions` 表 / vim 命名空间预留：为未来功能预建总线
  是过度设计（现有 `Change` 订阅 + 小字段够用）；vim 非目标，预留无意义。
- M1 行数门改红线：`input/state.rs` 剩余主要是表单字段 + Context-bound 编排，
  硬拆只是换地方堆行数；冻结新功能进入比追数字诚实。

## 8. 方案优缺点对比

| 维度 | A. 维持现状 | B. 仅 feature 门 | C. 抽核+组合（本方案） | D. 全复制分叉 |
|------|------------|-----------------|----------------------|--------------|
| 表单用户体感 | 差：70 个方法全可见，编辑器能力全编译 | 中：API 隐藏了，类型还是同一个 | 好：`Input` 干净小巧 | 好 |
| 二进制体积 | 大：1600 行编辑器代码常驻 | 小：特性关闭即瘦 | 小 | 最小（但省的只是 1600 行里的零头，大头 rope/布局两边都要） |
| 工作量 | 0 | 几天 | 4~6 周 | 6~10 周（含双倍回归） |
| 回归风险 | 0 | 接近 0（零行为变化） | 中（500+ 单测 + IME 手测兜底） | 高（两套 IME/装饰/折叠各自踩坑） |
| 后续扩展性 | 差：加功能继续改 state.rs/element.rs，文件越堆越大 | 差：门多了，结构没变 | 好：新功能只加文件+订阅 hook+扩展表 | 中：两边各加一遍，长期分叉 |
| 维护成本 | 低（短期）/ 高（长期，改一处想两处） | 低 | 中（多一套 core 抽象要学） | 高（双倍 bug，双倍单测，双倍文档） |
| 对 1.2 工期 | 无影响 | 可发版 | P0 可发，P1 起排后 | 直接延期 |
| 外部消费方 | 无影响 | 无影响 | P1/P2 无影响，P3 仅 CodeEditor 用户动 | 12 个消费方全部二选一 |

结论：A 是温水煮青蛙（短期零成本，长期每个新功能都在 3000 行文件里肉搏）；
B 是止痛药（见效快但不治本，结构问题一个没动）；D 是截肢（病灶和健康组织
一起切，还得装两个假肢）；C 是手术（疼几周，出来后两条腿各走各的）。
选 C 的核心理由就一条：**共享核只有一份，修一次两边好**——IME 三连 panic
要是发生在 D 方案里，我们现在要在两个仓库里各修三遍。

## 9. 真专属 vs 假专属（回应"普通输入框不需要 IME/装饰/折叠"）

逐项验到代码，结论是**对一半**：

### 9.1 真专属（分叉能甩掉，但 C 方案同样甩得掉）

折叠（fold_map + 折叠 UI）、高亮接线、多光标、行操作、括号匹配、当前行、
大纲、电缩进、行号 gutter——普通输入框确实一个不需要。注意：C 方案用
`editor` feature 门 + `EditorState` 照样把它们挡在表单之外，分叉在这一项上
**没有独家优势**。

### 9.2 假专属（分叉也甩不掉）

- **IME 不是编辑器功能**：`replace_and_mark_text_in_range`
 （`state.rs:2806`）无 mode 门控，只查 `disabled/read_only`；平台 IME
  对聚焦的单行框一样走合成路径（第一次 editor 崩溃堆栈就是该路径，
  与 mode 无关）。砍掉它 = 中文用户连搜索框都输不了中文。分叉对此只有
  两个选择：复制一份（双倍踩坑，原 §8 判断成立）或共享一个 IME 模块
  （那就不是分叉，是抽核 = C 方案）。
- **剪贴板/撤销同理**：表单刚需（Ctrl+C/V/Z），单行框缺了就是残次品。
- **装饰存储**：空集合零成本；`adjust_for_edit` 每次编辑全集合过一遍，
  空集合直接跳过。真要省字节，C 的 feature 门同样省。
- **display_map**：折叠投影可拆，但软换行映射是 textarea 刚需——display_map
  得拆成 wrap/fold 两半，**这笔钱分叉和抽核都要付，一样多**。

### 9.3 修正后的 D 方案评估

D 能甩掉的（§9.1），C 全能甩；D 甩不掉的（IME/剪贴板/撤销/换行映射），D
要么复制踩坑、要么回头共享——至此 D 相对 C 的真实优势只剩"名字好听"，
代价是 12 个消费方二选一 + 双倍回归。维持选 C。
